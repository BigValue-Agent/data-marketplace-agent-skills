# 조건에 맞는 단지 찾기

사용자의 조건을 데이터로 확인할 수 있는 질문으로 바꾸고, 후보를 찾아 충족 근거와
남은 불확실성을 보여준다. 지역·유형·지표·후보 수·상품 조합을 미리 고정하지 않는다.
예시 밖의 조건도 같은 방식으로 해석하되, 상품에 없는 사실을 만들어 범용성을 넓히지 않는다.

## 결과 원칙

- 기본 결과는 조건 요약, 후보 목록, 충족 근거, 조회 범위가 읽히는 간결한 Markdown이다.
  파일형 리포트를 원하면 [assets/report.html](assets/report.html)을 사용한다.
- 파일 업로드나 지도는 전제하지 않는다. 자연어 요청과 연결된 데이터로 시작한다.
- 결과의 단위는 단지다. 호·계약 행은 조건을 뒷받침하는 근거로 쓸 수 있지만, 현재 거래할
  수 있는 매물·호가·중개 연락처처럼 표현하지 않는다.
- ‘찾아서 비교해줘’는 먼저 조건으로 후보를 구성한 뒤 비교한다. 사용자가 이미 정한 대상의
  장단점·우선순위가 중심이면 비교 스킬을 사용한다. 다른 스킬 설치를 필수 의존성으로 만들지 않는다.

## 데이터 접근

현재 환경의 MCP 상품 도구 또는 공개 API 중 사용 가능한 경로를 선택한다. API 계약은
`https://datamarket.bigvalue.ai/llms.txt`에서 필요한 최신 상품 문서만 따라간다.
인증 절차·키 입력·특정 서버 주소를 이 스킬에서 고정하지 않는다. 연결할 수 없으면 그 상태를
알리고, 조회하지 않은 후보나 수치를 결과로 채우지 않는다.

## 진행 순서

1. **조건을 해석한다.** 지역, 주거 유형, 필수 조건, 선호, 제외 조건, 기간, 결과 개수를
   구분한다. AND·OR 관계와 경계값을 보존한다. 면적·가격처럼 해석에 따라 후보가 달라지는
   모호함만 확인한다. 특히 `최근·현재·예산 안`이 최신 값 판정인지 일정 기간 안의 조건 충족
   기록 존재 여부인지에 따라 결과가 달라지면 조용히 바꾸지 않는다. 문맥에서 해결한 해석은
   짧게 밝히고 이미 받은 정보를 다시 묻지 않는다.
2. **조건마다 근거를 정한다.** [references/product-guide.md](references/product-guide.md)를
   읽어 필드 직접 판정, 유효한 계산·상품 연결, 현재 확인 불가를 구분한다. API 필터가 없어도
   반환 필드로 판정할 수 있다. 필요 없는 호·가격·지도 상품까지 일괄 호출하지 않는다.
3. **후보 모집단을 확보한다.** 이름 검색은 지역과 대상을 식별하는 용도다. 지역 안에서
   찾는 요청은 지역 단지 목록으로 이어 간다. 사용자가 후보 집합을 줬다면 그 집합에서 시작한다.
   이름으로 중복을 제거하지 말고 문자열 식별자를 보존한다.
4. **필요한 깊이만 조회한다.** 먼저 단지 수준에서 확실히 탈락하는 후보를 걸러 낸 뒤,
   남은 조건에 필요한 상세 근거를 붙인다. [references/search-strategy.md](references/search-strategy.md)의
   페이지·조기 종료·존재 조건·결측 처리 규칙을 적용한다. 이미 받은 응답에 필요한 근거가 있으면
   재사용하고, 재집계·출력 검증만을 위해 동일 요청을 반복하지 않는다. 일부만 확인했으면 결과
   범위도 일부로 한정한다.
5. **충족·미충족·확인 불가를 판정한다.** 같은 호나 계약을 가리키는 조건은 같은 행 또는
   검증된 식별자 연결에서 함께 충족해야 한다. 필수 조건의 미확인 값을 충족으로 넣지 않는다.
   선호를 충족하지 못했다는 이유만으로 제외하거나, 부족한 후보를 채우려고 조건을 완화하지 않는다.
6. **사용자가 선택할 수 있게 쓴다.** 짧은 조건·범위 설명 뒤에 후보 이름과 핵심 조건의
   실제 값·단위·시점을 먼저 제시한다. 충족 후보와 추가 확인이 필요한 후보를 구분하고,
   후보가 없으면 없음 또는 판단 보류의 이유를 먼저 설명한다. 부분 조회·모집단 한정·미확인
   조건은 결과 옆에 남기고 상세 선정 과정은 뒤로 보낸다. 정렬은 사용자 기준을 우선하며
   임의 종합점수를 만들지 않는다. 후보 수가 많으면 표시 범위와 나머지 제공 방식을 밝힌다.
   탈락·판단 보류 후보의 전체 목록은 사용자가 요청했거나 선택에 직접 필요할 때만 보여주고,
   그렇지 않으면 개수와 주된 이유를 한 문장으로 요약한다.
   원 단위로 확인한 금액은 [scripts/format_money.py](scripts/format_money.py)의
   `format_money(value)`로 표시한다. 생성 코드에서 이 파일을 복사해 import하거나 CLI로
   실행한다. 계약 금액은 기본값으로 보존하고, 평균 등을 반올림할 때만 `round_to`(원)를
   지정해 표시 정밀도를 밝힌다. 판정·집계는 원값으로 하고 HTML·Markdown·요약에는 같은
   변환 결과를 재사용한다. Python 실행이 불가능하면 단위를 재조합하지 않고 원 단위로 표시한다.

요청 유형별 힌트가 필요할 때만 [references/search-patterns.md](references/search-patterns.md)를 읽는다.
패턴은 조합 예시이며 지원 요청의 목록이나 고정 조회 순서가 아니다.

## 반드시 지킬 데이터 의미

- 동·읍·면·리와 시군구·시도를 구분하고 요청 범위를 임의로 넓히지 않는다. 여러 지역은
  각각 확인한 뒤 합친다. 역 주변처럼 행정 경계와 다른 범위는 실제 포함 영역을 확인한다.
- 단지 대표 주거 유형과 단지에 실제 포함된 유형은 다르다. 대표 유형 필터로 포함 유형
  전체를 찾았다고 단정하지 않는다.
- `standard_ym` 등 반환 기준시점을 사용한다. 당일 조회가 오늘의 매물 현황을 뜻하지 않는다.
- 단지 최근 6개월 평균 매매가는 면적이 섞인 단지 전체 요약이다. 특정 면적의 예산 조건에
  대신 넣지 않는다. 과거 실거래·산출시세·공시가격은 서로 다른 가격 근거다.
- 평형 라벨을 전용면적으로 환산하지 않는다. 면적 존재 조건은 실제 호실 또는 호별 가격
  행에서 확인한다. 전체 평형 구성비에 따른 순위는 제공하지 않으며 이를 위해 전체 호실을 열거하지 않는다.
- 거리값을 도보시간·통학 안전으로, 학교명을 학군 등급으로 바꾸지 않는다.
- 취소 거래는 유효 거래 조건에서 제외한다. 거래가 관측되지 않았다는 사실로 거래 가능성이나
  미래 가치를 판단하지 않는다. 실거래에는 호 연결 키가 없으므로 특정 호의 거래로 붙이지 않는다.
- 오류·사용량 제한·페이지 상한은 ‘조건에 맞는 곳 없음’이 아니다. 수치가 없으면 0이 아니라
  확인 불가다. 알려진 값만으로 확정되는 판정과 아직 확인이 필요한 판정을 구분한다.

## HTML은 질문에 맞게 구성한다

템플릿의 JSON에 실제 조회 결과만 넣는다. 조건, 범위 설명, 결과 섹션, 표 열, 후보별 근거는
모두 가변 배열이다. 특정 지역·가격 카드·후보 수·지도 영역을 필수로 만들지 않는다.
작은 목록은 표 하나로, 근거가 복잡한 후보는 상세 항목으로, 서로 다른 비교 축은 섹션을
나눠 표현할 수 있다. 같은 내용을 카드와 표에 반복해서 채울 필요는 없다.
표 열은 선택에 필요한 근거만 고르고, 주소·보조 설명은 셀의 `note`나 후보 상세 항목을 활용한다.

`subtitle`에는 지역·유형·시점·핵심 조건을 짧게, `coverage.summary`에는 결과 해석에 중요한
조회 한계를 쓴다. `sections`는 후보와 근거부터 배치하고, 상세 조건·조회 범위는 뒤에 둔다.

필요하면 마크업·스타일도 질문에 맞게 바꿀 수 있다. 조건 판정, 조회 범위, 기준시점과 출처는
유지한다. 긴 표는 의미별로 나누거나 전체 결과를 별도 파일로 제공하고 표시한 범위를 밝힌다.
이 파일은 조회가 끝난 뒤 읽는 문서다. 지도 SDK·외부 폰트·런타임 API 요청·인증 정보 없이
열려야 한다. Markdown·HTML의 사용자용 본문에는 익숙한 이름과 판단에 필요한 값을 쓴다.
내부 식별자·API 필드명·호출 과정은 근거 파일이나 별도 기술 부록으로 분리한다. 동명 단지는
주소로 구분하고, 선정 방법도 사용자가 선택할 때 이해할 수 있는 말로 설명한다.

JSON 직렬화 후 `<`를 `\u003c`로 치환해 HTML에 삽입한다. 렌더러는 문자열을 텍스트로만
다룬다. 원시 HTML을 데이터 셀에 넣거나 문자열을 스크립트 코드로 이어 붙이지 않는다.

## 완료 전 확인

- 요청 조건과 AND·OR, 필수·선호·제외 구분을 보존했는가?
- 같은 호의 면적·층·가격 조건을 서로 다른 호에서 가져와 합격시키지 않았는가?
- 조회한 범위에서 충족 근거가 있고, 없는 값·부분 조회·실패를 솔직하게 표시했는가?
- ‘없음’, ‘모두’, ‘상위’라는 표현을 뒷받침할 수집 범위나 종료 근거가 있는가?
  요약의 건수·기간·최솟값·최댓값도 해당 근거 집합에서 계산하고, 표·Markdown과 같은
  집계 결과를 사용했는가?
- 후보·핵심 근거 또는 없음의 이유가 상세 설명보다 먼저 나오며, 중요한 조회 한계가 곁에 있는가?
- 사용자용 본문과 표에 내부 코드·호출 과정·중복 설명이 남아 있지 않은가?
- 후보 수나 표 항목이 달라져도 출력이 읽히며, HTML의 빈 상태·좁은 화면·인쇄가 정상인가?
